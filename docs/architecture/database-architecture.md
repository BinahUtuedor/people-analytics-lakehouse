# Database Architecture

## Overview

The **People Analytics Lakehouse Platform** uses PostgreSQL as its
operational source database and Amazon S3 as the analytical data-lake
storage layer.

PostgreSQL stores governed reference data, employee master data,
workforce lifecycle events and transactional HR data generated by the
simulator. It is intentionally separated from downstream analytical
processing.

The target analytical architecture uses:

-   Amazon S3 for Raw, Bronze, Silver and Gold storage;
-   Apache Spark / PySpark on Amazon EMR for distributed processing;
-   Spark SQL for analytical transformations;
-   dbt for selected Gold analytical models and tests;
-   Power BI for business intelligence;
-   FastAPI for governed data-product delivery.

# 2. Reference Data

Reference data is governed centrally through YAML configuration.

``` text
reference_data/*.yml
        │
        ▼
reference_data/loader.py
        │
        ▼
quality/reference_data_checks.py
        │
        ▼
database/seed.py
        │
        ▼
PostgreSQL Reference Tables
        │
        ▼
Simulator
```

The simulator consumes controlled values from PostgreSQL rather than
maintaining duplicate hard-coded vocabularies.

Operational records continue storing descriptive values where the
current schema expects them, avoiding unnecessary downstream disruption.

------------------------------------------------------------------------

# 3. Employee Master

The `employees` table represents the latest known employee state.

It includes:

-   employee number;
-   identity attributes;
-   hire and termination dates;
-   employment status and type;
-   salary;
-   department;
-   job role;
-   location;
-   manager;
-   management status;
-   active status.

The employee master is reconciled with workforce event history through
the data-quality framework.

------------------------------------------------------------------------

# 4. Workforce Event Model

The platform separates current state from historical events.

``` text
employees
   │
   ├── recruitment
   ├── promotions
   ├── transfers
   └── employee_exits
```

Event tables record what happened. The employee master records the
resulting current state.

Quality checks verify that event history and current state remain
consistent.

------------------------------------------------------------------------

# 5. Transactional Workforce Tables

Employee activity is captured through:

``` text
attendance
payroll
leave_requests
training
performance_reviews
employee_surveys
manager_feedback
```

Effective-date controls ensure that workforce facts fall inside the
employee's valid employment window.

``` text
hire_date <= event_date <= termination_date
```

For active employees, the current date is used as the upper boundary.

------------------------------------------------------------------------

# 6. Employee Exit Architecture

Termination uses both current state and authoritative event history.

``` text
Employee
   │
   ├── termination_date
   ├── employment_status
   └── is_active

EmployeeExit
   │
   ├── exit_date
   ├── exit_type
   ├── exit_reason
   ├── voluntary_flag
   └── regrettable_flag
```

`EmployeeExit` represents the termination event, while `Employee` stores
the resulting current state.

------------------------------------------------------------------------

# 7. PostgreSQL Responsibilities

PostgreSQL owns:

-   operational HR data;
-   reference-data persistence;
-   employee lifecycle state;
-   workforce transactions and events;
-   source data for analytical extraction.

PostgreSQL is **not** the analytical warehouse.

``` text
PostgreSQL
    │
    ▼
Python Extraction
    │
    ▼
Raw Parquet
    │
    ▼
Amazon S3
    │
    ▼
Spark Analytical Processing
```

------------------------------------------------------------------------

# 8. Analytical Storage Architecture

The analytical platform uses Amazon S3.

``` text
Amazon S3
│
├── raw/
│   └── postgresql/
│
├── bronze/
│
├── silver/
│
└── gold/
```

The layers serve different purposes:

  Layer    Purpose
  -------- -----------------------------------------------------------
  Raw      Immutable, source-aligned extraction archive
  Bronze   Source-conformed records with technical metadata
  Silver   Cleansed, standardised and integrated analytical entities
  Gold     Business-ready domain analytical data products

Initial lakehouse storage uses Parquet to keep Spark workloads portable
across local development and Amazon EMR.

------------------------------------------------------------------------

# 9. Gold Data-Product Structure

Gold is organised by analytical domain.

``` text
gold/
├── workforce/
├── recruitment/
├── learning/
├── performance/
├── payroll/
└── attrition/
```

These domains expose reusable analytical datasets rather than forcing
consumers to understand low-level operational schemas.

# 12. Storage and Processing Separation

The mature architecture deliberately separates workload types.

``` text
PostgreSQL
    Operational HRIS

Amazon S3 Raw
    Immutable source archive

Amazon S3 Bronze / Silver / Gold
    Analytical storage

Amazon EMR
    Managed Spark execution

dbt
    Selected Gold analytical modelling

Governance Schemas
    Metadata and sharing policy

FastAPI
    Controlled data-product delivery
```

This prevents one database technology from being forced to handle
operational, analytical and governance workloads simultaneously.

# Design Principles

## Separation of Concerns

Each component has a defined responsibility:

``` text
Simulator       Synthetic HR generation
PostgreSQL      Operational source system
Quality         Validation and quality gates
ETL             Extraction and movement
Amazon S3       Durable analytical storage
PySpark / EMR   Bronze and Silver engineering
Spark SQL       SQL-based distributed transformations
dbt             Gold analytical modelling and tests
FastAPI         Governed data delivery
```

## Operational and Analytical Separation

Reporting, machine-learning and third-party analytical consumers should
not query PostgreSQL directly.

## Reference-Data-Driven Design

Controlled business values follow:

``` text
YAML → Validation → PostgreSQL → Simulator
```

## Event and Current-State Reconciliation

Recruitment, promotions, transfers and exits preserve historical events
while the employee master records current state.

## Data Quality as a Gate

Validation controls whether data is allowed to move to the next layer.

## Security by Design

Access is separated across PostgreSQL credentials, AWS IAM, curated Gold
datasets and API authorisation.

## Idempotency and Reproducibility

The platform supports controlled reruns through idempotent seeding,
batch identity, partitioned Raw storage, reconciliation and batch-aware
Spark processing.

## Traceability

Downstream products should be traceable to source data through
extraction IDs, batch IDs, source-file metadata and record hashes.

------------------------------------------------------------------------

# Summary

The database architecture deliberately keeps PostgreSQL focused on
operational HR data and governed reference data.

Analytical processing moves downstream:

``` text
PostgreSQL
    ↓
Amazon S3 Raw
    ↓
Bronze
    ↓
Silver
    ↓
Gold Data Products
```

Amazon EMR supplies scalable Spark execution without changing the
operational database design.
