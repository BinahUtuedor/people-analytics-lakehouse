# Project Overview

The **People Analytics Lakehouse Platform** is an end-to-end data engineering portfolio project that simulates the operation of an enterprise Human Resources Information System (HRIS) and transforms synthetic workforce data into governed analytical data products.

Rather than relying on static CSV datasets, the platform contains a Python-based simulation engine that generates realistic workforce entities and events across the employee lifecycle. These records are persisted to a PostgreSQL operational database, validated through a dedicated data-quality framework, extracted to Parquet, reconciled, and uploaded to an Amazon S3 Raw layer.

The target cloud architecture uses **Amazon EMR with PySpark and Spark SQL** for distributed Bronze and Silver processing. The platform is designed to support both **event-driven orchestration**, using Amazon S3 events and AWS Lambda, and scheduled orchestration for recurring workloads.

Gold-layer datasets are organised as domain-oriented analytical data products for workforce, recruitment, learning, performance, payroll and attrition analytics. These products are intended to support Power BI, advanced analytics, machine learning and governed API-based data sharing.

All workforce data generated by the project is synthetic.

# Business Problem

Organisations typically hold workforce information across multiple operational systems, including:

- Human Resource Information Systems (HRIS)
- Payroll systems
- Applicant Tracking Systems (ATS)
- Learning Management Systems (LMS)
- Performance management systems
- Attendance and absence systems
- Employee engagement platforms

When these systems operate independently, organisations can struggle to establish consistent definitions, trusted metrics and a unified view of the workforce.

This project demonstrates how an enterprise data platform can integrate and govern workforce information to support questions such as:

- How is workforce headcount changing over time?
- Which departments experience the highest employee turnover?
- What factors are associated with voluntary attrition?
- How do attendance and absence patterns vary across the organisation?
- What are the organisation's payroll and overtime trends?
- How effective are recruitment processes?
- How much learning and development activity is taking place?
- How does employee performance evolve over time?
- Which workforce trends should leadership monitor?

# Pipeline Orchestration

The target platform supports two complementary orchestration patterns.

## Event-Driven Processing

Event-driven processing is appropriate when downstream work should begin because new data has arrived.

```text
S3 Raw Object Created
        │
        ▼
    AWS Lambda
        │
        ▼
   EMR Spark Job
        │
        ▼
      Bronze
```

A Raw S3 object event can trigger Lambda, which identifies the dataset and batch and initiates the appropriate EMR PySpark workload.

## Scheduled Processing

Scheduled orchestration is appropriate for recurring workloads such as:

- operational extraction
- periodic data-quality reporting
- payroll processing
- Gold refreshes
- metadata publication
- maintenance tasks

A workflow orchestrator can be introduced where dependencies and recurring schedules justify it.

# Medallion Architecture

## Raw Layer

The Raw layer preserves extracted source data before analytical processing.

Current operational flow:

```text
PostgreSQL
    ↓
Python extraction
    ↓
Parquet
    ↓
Raw validation
    ↓
Amazon S3 Raw
```

Raw data provides the immutable source representation required for downstream processing, reconciliation and lineage.

## Bronze Layer

Bronze provides a source-conformed representation of Raw datasets with additional ingestion metadata.

The implemented Bronze process is:

```text
S3 Raw
   ↓
PySpark
   ↓
Schema / ingestion validation
   ↓
Technical metadata enrichment
   ↓
S3 Bronze
```

Bronze preserves source business values while adding technical metadata such as:

- `_bronze_ingested_at`
- `_source_system`
- `_source_table`
- `_source_file`
- `_batch_id`
- `_extraction_date`
- `_record_hash`

Initial Bronze storage will use Parquet on Amazon S3.

## Silver Layer

Silver will contain cleaned, validated, standardised and integrated datasets.

Transformations will include, where appropriate:

- explicit schema enforcement
- data-type standardisation
- null handling
- duplicate handling
- reference-data validation
- business-rule enforcement
- derived attributes
- cross-domain joins
- effective-date processing
- historical modelling

Silver processing will deliberately use both **PySpark DataFrame APIs and Spark SQL**.

## Gold Layer

Gold contains business-ready analytical data products rather than a single undifferentiated reporting layer.

```text
Gold
├── Workforce Analytics
├── Recruitment Analytics
├── Learning Analytics
├── Performance Analytics
├── Payroll Analytics
└── Attrition Analytics
```

Each product will expose governed, reusable analytical datasets for reporting and downstream consumption.

# Data Quality Framework

Data quality is treated as an architectural capability rather than a final reporting check.

Validation currently covers areas including:

- duplicate detection
- referential integrity
- employee hierarchy
- salary validity
- employment dates
- workforce lifecycle consistency
- exit-event consistency
- reference-data conformance
- extraction reconciliation
- Raw-layer validation

Examples of business-rule validation include:

- non-manager employees must have a manager
- termination dates cannot precede hire dates
- salaries cannot be negative
- active employees cannot have authoritative exit events
- exit events cannot occur before hire dates
- termination state must agree with authoritative exit events

As the lakehouse develops, quality checks will also be applied at Bronze, Silver and Gold boundaries.

# Amazon EMR and Spark Processing

Amazon EMR is the target managed execution environment for distributed PySpark and Spark SQL workloads.

Spark applications are designed to remain portable:

```text
Local Development
       │
       ▼
  spark-submit
       │
       ▼
Same Spark Application
       │
       ▼
 Amazon EMR
```

Production Spark code should therefore avoid Databricks-specific APIs and hard-coded local Spark masters.

EMR responsibilities will include:

- executing PySpark jobs
- processing S3 Raw datasets
- creating Bronze and Silver datasets
- handling distributed transformations
- supporting Spark SQL
- executing scalable joins and aggregations
- exposing Spark execution plans for optimisation

# Development Workflow

Local development follows a staged workflow so failures can be isolated to the relevant layer.

Current operational pipeline commands include:

```bash
python main.py validate
python main.py extract
python main.py validate-raw
python main.py upload-s3
python main.py raw-pipeline
python main.py full-refresh
```

The Bronze foundation is implemented as a separate `spark/bronze/job.py` job
and does not change the existing Raw pipeline or root CLI. The complete Bronze
suite, including physical Parquet lineage and duplicate-publication tests, runs
in the Linux `spark-tests` Docker service. All 17 supported datasets in batch
`fc4e3604-70f2-43f8-96ff-419e9d3046e5` have passed transformation,
validation, 885,037-to-885,037 row-count reconciliation and duplicate-safe
publication.

Run the authoritative complete suite from Windows or another Docker host with:

```powershell
docker compose run --rm --build spark-tests
```

Native Windows remains supported for ordinary Python development, mocked AWS
tests and in-memory Spark work. Hadoop-backed local filesystem integration uses
Linux Docker; the project deliberately does not ship unofficial `winutils.exe`
binaries or add Windows-specific behavior to production Spark code. See
`docs/development/spark-local-development.md` for the runtime versions and
workflow.

The intended progression is:

```text
Working Raw Pipeline
        ↓
Local Bronze Spark Job
        ↓
Bronze Validation
        ↓
Manual EMR Execution
        ↓
Event-Driven Lambda Trigger
        ↓
Silver Processing
```

# Engineering Principles

The project follows several core principles:

### Separation of Concerns

Simulation, operational storage, validation, extraction, distributed processing, analytics and serving are implemented as separate responsibilities.

### Portability

Spark transformation code is designed to run locally during development and on Amazon EMR in AWS.

### Configuration over Hard-Coding

Environment-specific values and controlled reference values are externalised wherever appropriate.

### Data Quality by Design

Quality validation is performed at multiple boundaries rather than only after analytics models have been produced.

### Traceability

Batch identifiers, technical metadata and lineage allow data to be traced from operational source through analytical consumption.

### Idempotency

Pipeline components should support safe reruns without silently duplicating previously processed batches.

### Security by Design

AWS workloads will use IAM roles and least-privilege access. Operational data will not be exposed directly to external consumers.

### Incremental Delivery

Each platform capability is implemented, tested and validated before dependent layers are introduced.
